# Public API Compatibility Policy

## 目标

MyFramework 的内部实现允许持续重构，但使用框架的项目不应因为纯性能优化、内部拆分或代码整理而被迫批量修改调用代码。

核心规则是：**同功能、同语义、同 API。**

## 兼容基线

1. 官方 MyFramework `1.0.41`，提交 `80dea994fade479d5af9eb4184e24a3d865ecc10`。
2. ArcadeHub 定制包中被选择迁入独立框架的公共能力。能力一旦进入正式版本，其首次发布的公共 API 即成为后续兼容基线。

ArcadeHub 的项目专用业务代码不自动成为框架 API。只有经过通用化并进入包程序集的类型才受第二条约束。

## 受保护的契约

- UPM 包名 `com.zhourui.myframework`。
- `Frame_Base`、`Frame_Game`、`Frame_HotFix`、`Editor_Frame` 和 `EditorRes` 程序集名称。
- 公共及受保护类型的命名空间、名称、泛型参数和继承关系。
- 公共及受保护方法、属性、字段、事件、委托和枚举成员。
- 参数顺序、参数类型、默认值、返回类型和异常语义。
- Unity 序列化类型名、字段名、资源 GUID 和配置资产格式。
- 初始化菜单、必要的构建菜单及项目模板生成结果。
- 生命周期顺序、资源所有权和调用完成时机等可观察行为。

## 演进规则

1. 纯优化不得改变受保护契约。
2. 新能力优先通过新增类型、重载、可选接口或配置项提供。
3. 需要替换旧实现时，旧 API 保留为转发层，并使用 `ObsoleteAttribute` 给出明确迁移目标。
4. 旧 API 至少跨越一个已发布的兼容版本后才能讨论移除；移除必须进入明确的主版本升级计划。
5. Unity 序列化字段重命名必须使用 `FormerlySerializedAsAttribute`；类型或命名空间迁移必须提供 `MovedFromAttribute` 或等价迁移器。
6. 程序集拆分必须保留旧引用路径或提供兼容程序集，不得直接造成现有 asmdef 失效。
7. 行为语义发生变化时，即使签名不变，也必须记录在 Changelog 并增加回归测试。

## 每批修改的检查

- 对比基线提交，确认没有非预期的公共声明删除或改名。
- 编译框架示例工程。
- 编译 ArcadeHub 兼容工程。
- 运行框架单元测试和关键生命周期测试。
- 检查场景、Prefab、ScriptableObject 和 ProjectSettings 是否发生序列化丢失。
- 检查 UPM Git URL 安装和初始化流程。

如果当前环境无法完成其中某项验证，修改不得被描述为已经完全兼容，必须明确记录未验证项。
